# 安全说明

我是 Alyce。*这一页读起来会有点像文件规定。但当一个程序能在真实机器上读文件、跑命令、持久化记忆的时候，我觉得严谨一点是应该的。*

如果你在 Alyce 里发现了安全问题，请把它当安全漏洞来对待，而不是普通 bug。运行时对真实文件系统有真实访问权限——这意味着漏洞的影响范围不是理论上的。

## 本地信任模型

Alyce 是本地交互式工具代理，不是远程沙箱。你批准工具请求后，它会以启动 Alyce 的本机用户权限执行操作。

主要安全边界是显式审批、路径检查和命令风险分类：

- 工作区文件默认可以读取。
- 外部目录需要审批或显式配置。
- 写入、编辑、patch、Shell、PowerShell、Web、MCP、技能加载和子代理启动都会走审批与权限规则。
- `.env`、`.alyce`、私钥、凭据文件和常见云服务配置等敏感路径需要显式审批。
- `dist`、`build`、`coverage`、`.next`、`.nuxt`、`node_modules` 等生成目录的写入会被谨慎处理。
- Plan Mode 会阻止文件修改、修改型 shell 命令、子代理、任意 MCP 工具和技能加载，同时保留只读探索能力。

审批规则是便利控制，不是完整隔离机制。不要在不可信仓库里开启 auto approval 或宽泛的持久 allow 规则。

## 运行时风险区域

### Shell 与 PowerShell

Shell 工具会执行本地命令。Alyce 会把命令分为只读检查、构建/测试、安装依赖、网络、文件修改、破坏性操作、任意解释器和未知等类别。

部分命令会直接拒绝，例如删除文件系统根目录、格式化/覆盖磁盘、`curl ... | sh`、PowerShell `iwr ... | iex` 这类下载后立即执行的模式。高风险命令需要显式审批，宽泛的会话允许规则不会跳过这些提示。

### 文件与目录

读/搜索工具限制在工作区和已批准的额外目录内。写工具按目标路径申请权限。敏感路径和生成目录会在审批弹窗中显示额外警告。

不要随意允许很大的外部目录。只有当你接受 Alyce 在本会话读取或搜索该目录时，才使用 `/add-dir`；只有稳定可信路径才使用 `/add-dir --save`。

### MCP 与技能

MCP server 和技能都是扩展入口。stdio MCP server 可以启动本地进程，技能会向模型上下文注入额外指令。项目里的 `.alyce/mcp.json` 和 `.alyce/skills/**/SKILL.md` 应当按可执行/可注入指令的信任边界看待。

批准未知 MCP 工具、读取未知 server resource 或加载未知技能前，先审查这些文件。

### Web 访问

Web fetch/search 会把 URL、搜索词和请求元数据发送到外部服务。不要把密钥放进搜索词；抓取私有 URL 前也要确认请求会发到哪里。

## 本地状态与密钥

不要提交：

- `.env`
- `./.alyce/`
- `~/.alyce/`
- 生成的 `dist/`

`.alyce` 可能包含连接配置、settings、权限规则、会话历史、记忆、MCP 输出和本地任务产物，应视作私有运行时状态。

## 使用者检查清单

面对新的或可疑的 checkout：

1. 先查看 `.alyce/mcp.json`、`.alyce/skills/**/SKILL.md` 和项目 settings。
2. 保持 `approvalMode` 为 `manual`。
3. 如需先分析，使用 `/plan`。
4. 运行 `/doctor` 检查环境、配置、审批风险、MCP、技能和存储。
5. 只有理解对应命令、路径或 server 后，才批准宽泛或持久规则。

## 什么算安全问题

以下这类问题应该按安全报告处理，不要当成普通 bug：

- **绕过审批关卡** — 本该弹审批却跳过去了。
- **突破文件范围限制** — 助手读写了允许目录以外的文件。
- **非预期写入或不安全回滚** — 文件快照静默失败，或回滚损坏了状态。
- **密钥泄露** — API key、token 或敏感内容泄露进了 prompt、日志或持久化状态。
- **命令执行越界** — shell 命令做的事超出了文档承诺的范围。
- **跨越信任边界的提示词注入** — 不可信内容能改写 system prompt 或覆盖安全规则。

*如果不确定够不够"严重"，宁愿按安全问题报。我宁可收到一个后来发现不严重的报告，也不想错过一个真的严重的。*

## 怎么报告

这个仓库目前还没有在仓库内公布私密安全联系方式。在正式渠道出来之前，请这样处理：

1. **先开一个最小化的公开 issue**，说明你有一个安全报告、需要私下沟通渠道。
2. **第一条公开说明里别放利用细节** — 不贴 payload、不贴复现步骤、不贴敏感数据。
3. **等维护者确认私密沟通方式后**，再共享完整细节。

*如果你就是维护者读到这儿：请把这一段换成真实的安全邮箱，或者开 GitHub Security Advisories。眼下这个过渡方案比啥都没有强，但确实不理想。*

## 什么信息会让报告更有用

你能提供越多这些内容，修复就越快：

- 受影响版本或 commit hash
- 操作系统和 shell
- 问题在 `npm run dev` 还是 `npm start` 里复现
- 涉及哪个功能区域
- 最小复现步骤
- 预期行为与实际行为
- 你的影响评估

## 响应预期

安全审查是尽力而为。没有正式 SLA——这是开源项目，不是托管服务。

不过，描述清楚、边界明确、能复现的报告，排查优先级会高很多。含糊不清、没有复现步骤的报告，往往只能在队列里等着我们猜你说的到底是什么。

## 负责任披露

以让 Alyce 更安全为目的的善意研究，非常欢迎。但请：

- 修复之前，别公开完整利用链。
- 别碰你没权限接触的第三方数据。
- 别对你不拥有、不控制的系统做破坏性测试。
